* Part 1: Building User Interfaces

* A Basic Component

#+begin_src rust
#[component]
fn App() -> impl IntoView {
    let (count, set_count) = create_signal(0);

    view! {
        <button
            on:click=move |_| {
                // on stable, this is set_count.set(3);
                set_count(3);
            }
        >
            "Click me: "
            // on stable, this is move || count.get();
            {move || count()}
        </button>
    }
}
#+end_src

- ~#[component]~ annotates a function so it can be used as a component
  in your Leptos application.
- Component is a function that takes zero or more argument of any type
  and returns ~impl IntoView~.
- *create_singal* creates a signal, the basic unit of reactive change
  and state management in Leptos. It returns ~(getter, setter)~

** Using signals

| Type | Nightly     | Stable          |
|------+-------------+-----------------|
| Get  | count()     | count.get()     |
| Set  | set_count() | set_count.set() |

Docs:

- [[https://docs.rs/leptos/latest/leptos/struct.ReadSignal.html][ReadSignal]]
- [[https://docs.rs/leptos/latest/leptos/struct.WriteSignal.html][WriteSignal]]

* Dynamic classes

- Class syntax: ~class:~
  - Takes class name, following the colon.
  - A value which can be a bool or a function that returns a
    bool. When value is true, class is added.

#+begin_src rust
class:red=move || count() % 2 == 1
#+end_src

Or

#+begin_src rust
class=("red", move || count() % 2 == 1)
#+end_src

* Dynamic styles

#+begin_src rust
style:left=move || format!("{}px", x() + 100)
#+end_src

* Dynamic attributes

#+begin_src rust
<progress
    max="50"
    // signals are functions, so `value=count` and `value=move || count.get()`
    // are interchangeable.
    value=count
/>
#+end_src

* Forms and Inputs

** Controlled Inputs

- In a "controlled input" the framework controls the state of the input element.

#+begin_src rust
#[component]
fn SomeInput() -> impl IntoView {
    let (name, set_name) = create_signal("Controlled input".to_owned());
    let input_handler = move |ev| {
        set_name(event_target_value(&ev));
    };
    view! {
        <input type="text" on:input=input_handler prop:value=name />
        <p>"Name is: " {name}</p>
    }
}
#+end_src

** Uncontrolled Input

- In an uncontrolled input, the browser controls the state of the
  input element.

#+begin_src rust
#[component]
fn SomeInput() -> impl IntoView {
    let (name, set_name) = create_signal("Uncontrolled input".to_owned());
    let input_element: NodeRef<html::Input> = create_node_ref();
    let on_submit = move |ev: SubmitEvent| {
        // To stop page from reloading
        ev.prevent_default();
        let value = input_element().expect("<input> should be mounted").value();
        set_name(value);
    };
    view! {
        <form on:submit=on_submit>
        <input type="text" value=name node_ref=input_element />
        <input type="submit" value="Submit" />
        </form>
        <p>"Name is: " {name}</p>
    }
}
#+end_src

- NodeRef is a kind of reactive smart pointer: we can use it to access
  the underlying DOM node.

* Control and Flow

Code like this can be problematic:

#+begin_src rust
#[component]
fn App() -> impl IntoView {
    let (count, set_count) = create_signal(0);
    let message = move || {
        if count() > 5 {
            logging::log!("{}: rendering Big", count());
            "Big"
        } else {
            logging::log!("{}: rendering Small", count());
            "Small"
        }
    };

    view! {
        <button
        class:red=move || count() % 2 == 1
            on:click=move |_| {
                set_count.update(|n| *n += 1);
            }
        >
            "Click me: "
            {move || count()}
        </button>
        <p>{message}</p>
    }
}
#+end_src

When you press this button, this would be the behavior:
- rendering Small
- rendering Small
- rendering Small
- rendering Small
- rendering Small
- rendering Big
- rendering Big
...

The problem is every time count changes, message is being computed again.

** <Show/>

- Solution for the above problem. Memoizes the ~when~ condition.

#+begin_src rust
#[component]
fn Big() -> impl IntoView {
    logging::log!("Rendering big");
    "Big"
}

#[component]
fn Small() -> impl IntoView {
    logging::log!("Rendering small");
    "Small"
}

#[component]
fn App() -> impl IntoView {
    let (count, set_count) = create_signal(0);
    view! {
        <button
        class:red=move || count() % 2 == 1
            on:click=move |_| {
                set_count.update(|n| *n += 1);
            }
        >
            "Click me: "
            {move || count()}
        </button>
        <Show
          when=move|| {count() > 5}
          fallback=|| view! {<Small/> }
        >
        <Big/>
        </Show>
    }
}
#+end_src

When you press this button, this would be the behaviour:
- Rendering small
- Rendering big

Only two log statements. No more heavy computation, yay!

* Type Conversions

- ~view~ macro doesn't return the most generic wrapping [[https://docs.rs/leptos/latest/leptos/enum.View.html][View]]
  type. Instead it returns types like ~Fragment~ or
  ~HtmlElement<Input>~.

Following code will result in a compile error:

#+begin_src rust
#[component]
fn App() -> impl IntoView {
    let (count, set_count) = create_signal(0);
    let is_odd = move || count() & 1 == 1;
    view! {
        <div> {
            move || match is_odd() {
                true if count() == 1 => {
                    // returns HtmlElement<Pre>
                    view! {<pre>"One"</pre>}
                },
                false if count() == 2 => {
                    // returns HtmlElement<P>
                    view! {<p>"Two"</p>}
                },
                // returns HtmlElement<Textarea>
                _ => view! { <textarea>{count()}</textarea>}
            }
        }
        <button
        class:red=move || count() % 2 == 1
            on:click=move |_| {
                set_count.update(|n| *n += 1);
            }
        >
            "Click me: "
            {move || count()}
        </button>
        </div>
    }
}
#+end_src

Error:

#+begin_src sh
= note: expected struct `leptos::HtmlElement<Pre>`
	   found struct `leptos::HtmlElement<P>`
#+end_src

Two possible fixes:
- Use *into_any()* to convert it to ~HtmlElement<AnyElement>~
- Convert them into view via *into_view()*

Solution with proper type conversion:

#+begin_src src
#[component]
fn App() -> impl IntoView {
    let (count, set_count) = create_signal(0);
    let is_odd = move || count() & 1 == 1;
    view! {
        <div> {
            move || match is_odd() {
                true if count() == 1 => {
                    // returns HtmlElement<Pre>
                    view! {<pre>"One"</pre>}.into_any()
                },
                false if count() == 2 => {
                    // returns HtmlElement<P>
                    view! {<p>"Two"</p>}.into_any()
                },
                // returns HtmlElement<Textarea>
                _ => view! { <textarea>{count()}</textarea>}.into_any()
            }
        }
        <button
        class:red=move || count() % 2 == 1
            on:click=move |_| {
                set_count.update(|n| *n += 1);
            }
        >
            "Click me: "
            {move || count()}
        </button>
        </div>
    }
}
#+end_src

* Error handling

- Code to build a number widget:

#+begin_src rust
#[component]
fn NumericInput() -> impl IntoView {
    let (value, set_value) = create_signal(Ok(0));

    // when input changes, try to parse a number from the input
    let on_input = move |ev| set_value(event_target_value(&ev).parse::<i32>());

    view! {
        <label>
            "Type an integer (or not!)"
            <input type="number" on:input=on_input/>
            <p>
                "You entered "
                <strong>{value}</strong>
            </p>
        </label>
    }
}
#+end_src

Problem with the above code:
- No error handling!
- Users won't know what's the issue

Solution: ~<ErrorBoundary />~ component. (Similar solution like ~<Show />~)

Fixed code:

#+begin_src rust
#[component]
fn NumericInput() -> impl IntoView {
    let (value, set_value) = create_signal(Ok(0i32));

    // when input changes, try to parse a number from the input
    let on_input = move |ev| set_value(event_target_value(&ev).parse::<i32>());

    let error_handler = |errors: RwSignal<Errors>| {
        view! {
            <div class="error">
            <p>"Not a number! Errors: " </p>
            <ul>
            {
                move || errors.get().into_iter().map(|(_, e)| view! {<li>{e.to_string()}</li>}).collect_view()
            }
            </ul>
            </div>
        }
    };

    view! {
        <label>
            "Type an integer (or not!)"
            <input type="number" on:input=on_input/>
        <ErrorBoundary fallback=error_handler>
            <p>
                "You entered "
                <strong>{value}</strong>
            </p>
        </ErrorBoundary>
        </label>
    }
}
#+end_src

* Parent Child communication

- We already saw how to communicate between a parent and a child via
  props: Use ReadSignal, a Signal or MaybeSignal as a prop.
- But how can a child communicate with a parent ? ie sending state
  changes back to the parent.

** Pass a WriteSignal

#+begin_src rust
#[component]
pub fn App() -> impl IntoView {
    let (toggled, set_toggled) = create_signal(false);
    view! {
        <p>"Toggled? " {toggled}</p>
        <ButtonA setter=set_toggled/>
    }
}

#[component]
pub fn ButtonA(setter: WriteSignal<bool>) -> impl IntoView {
    view! {
        <button
            on:click=move |_| setter.update(|value| *value = !*value)
        >
            "Toggle"
        </button>
    }
}
#+end_src

Cons:
- Hard to reason your code.

** Use a Callback

#+begin_src rust
#[component]
pub fn App() -> impl IntoView {
    let (toggled, set_toggled) = create_signal(false);
    view! {
        <p>"Toggled? " {toggled}</p>
        <ButtonB on_click=move |_| set_toggled.update(|value| *value = !*value)/>
    }
}


#[component]
pub fn ButtonB(#[prop(into)] on_click: Callback<MouseEvent>) -> impl IntoView
{
    view! {
        <button on:click=on_click>
            "Toggle"
        </button>
    }
}
#+end_src

Cons:
- Logic to mutate signal exists in ~<App />~ and not in ~<ButtonB />~

*** Use Closure instead of Callback

#+begin_src rust
#[component]
pub fn App() -> impl IntoView {

    view! {
        <p>"Toggled? " {toggled}</p>

#[component]
pub fn ButtonB<F>(on_click: F) -> impl IntoView

    F: Fn(MouseEvent) + 'static,

    view! {
        <button on:click=on_click>
            "Toggle"
        </button>
    }
}
#+end_src

Cons:
- Logic to mutate signal exists in ~<App />~ and not in ~<ButtonB />~

** Use an Event Listener

#+begin_src rust
#[component]
pub fn App() -> impl IntoView {
    let (toggled, set_toggled) = create_signal(false);
    view! {
        <p>"Toggled? " {toggled}</p>
        // note the on:click instead of on_click
        // this is the same syntax as an HTML element event listener
        <ButtonC on:click=move |_| set_toggled.update(|value| *value = !*value)/>
    }
}


#[component]
pub fn ButtonC() -> impl IntoView {
    view! {
        <button>"Toggle"</button>
    }
}
#+end_src

- This works by adding ~on:~ event listener to *each* element that
  ~<ButtonC/>~ returns. (In this case it's just one button)

** Providing a Context

Imagine having a deeply nested component tree:

#+begin_src rust
#[component]
pub fn App() -> impl IntoView {
    let (toggled, set_toggled) = create_signal(false);
    view! {
        <p>"Toggled? " {toggled}</p>
        <Layout/>
    }
}

#[component]
pub fn Layout() -> impl IntoView {
    view! {
        <header>
            <h1>"My Page"</h1>
        </header>
        <main>
            <Content/>
        </main>
    }
}

#[component]
pub fn Content() -> impl IntoView {
    view! {
        <div class="content">
            <ButtonD/>
        </div>
    }
}

#[component]
pub fn ButtonD<F>() -> impl IntoView {
    todo!()
}
#+end_src

Now <ButtonD/> is no longer a direct child of <App/>, so you can’t
simply pass your WriteSignal to its props. You can do something called
"prop drilling", but that will lead to a mess.

Soluting: Using the Context API. :-)

#+begin_src rust
#[component]
pub fn App() -> impl IntoView {
    let (toggled, set_toggled) = create_signal(false);
    // share `set_toggled` with all children of this component
    provide_context(set_toggled);
    view! {
        <p>"Toggled? " {toggled}</p>
        <ButtonC/>
    }
}

#[component]
pub fn ButtonC() -> impl IntoView {
    let setter = use_context::<WriteSignal<bool>>().expect("to have found the setter provided");
    let handler = move |_| setter.update(|value| *value = !*value);
    view! {
        <button on:click=handler>"Toggle"</button>
    }
}
#+end_src

Cons:
- Should be used with caution as it allows you to mutate state from
  arbitrary parts of the code.

Pros:
- No performance downsides.

* Components Children

- Motivation: Passing component to a component.

Two ways:
- *render props*: Properties that are function that return a view.
- the *children* prop: Special component property that includes
  anything you pass as a child to the component. (We already saw that
  in ~<Show />~ component)

Example showing both the above ways:

#+begin_src rust
#[component]
pub fn App() -> impl IntoView {
    view! {
        <TakesChildren render_prop=|| view!{ <p>"From render prop!"</p>}>
        <p>"Hello world"</p>
        </TakesChildren>
    }
}

#[component]
pub fn TakesChildren<F, IV>(
    /// Takes a function (type F) that returns anything that can be
    /// converted into a View (type IV)
    render_prop: F,
    /// `children` takes the `Children` type
    children: Children,
) -> impl IntoView
where
    F: Fn() -> IV,
    IV: IntoView,
{
    view! {
        <h2>"Render Prop"</h2>
        {render_prop()}

        <h2>"Children"</h2>
        {children()}
    }
}
#+end_src

** Manipulating Childrens

#+begin_src rust
#[component]
pub fn App() -> impl IntoView {
    view! {
        <WrapsChildren>
            "A"
            "B"
            "C"
        </WrapsChildren>
    }
}

#[component]
pub fn WrapsChildren(children: Children) -> impl IntoView {
    // Fragment has `nodes` field that contains a Vec<View>
    let children = children()
        .nodes
        .into_iter()
        .map(|child| view! { <li>{child}</li> })
        .collect_view();

    view! {
        <ul>{children}</ul>
    }
}
#+end_src
